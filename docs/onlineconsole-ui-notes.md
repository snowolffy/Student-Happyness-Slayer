# OnlineConsole — บันทึกการออกแบบ UI (2026-09-04)

บันทึกไว้เพื่อกันไม่ให้ของที่ตั้งใจทำถูก "แก้กลับ" ในอนาคต เอกสารนี้ครอบคลุมเฉพาะ
`src/OnionProcOparetor.OnlineConsole` (Blazor Server) ไม่เกี่ยวกับ WPF Console

## 1. กับดักที่ต้องรู้ก่อนแก้ไฟล์ layout

แอปนี้ใช้ **per-page interactivity**: `Program.cs` ลงทะเบียน `AddInteractiveServerComponents()`
และแต่ละ page ใส่ `@rendermode InteractiveServer` เอง ส่วน `<Routes />` ใน `App.razor` ไม่ได้ใส่
(ตั้งใจ — ถ้าใส่ ทั้งแอปจะกลายเป็น interactive แล้ว `Login`/`ChangePassword` ที่ต้อง POST เข้า
`AuthEndpoints` จริง ๆ จะพัง เพราะ `SignInAsync` ต้องการ response ที่ยังไม่ถูก stream ออกไป)

ผลที่ตามมาซึ่ง **มองไม่เห็นจากการอ่านโค้ด**:

> `MainLayout.razor` / `NavMenu.razor` / `TabBar.razor` ถูก render แบบ **static เสมอ**
> และทำให้ interactive ไม่ได้ด้วย เพราะ `@Body` เป็น `RenderFragment` ซึ่ง serialize เป็น
> root component parameter ไม่ได้ (เป็นข้อจำกัดที่ Microsoft ระบุไว้ ไม่ใช่บั๊ก)
> → `@onclick` ใน layout **ไม่เคยทำงาน**

บั๊กจริงที่เกิดจากเรื่องนี้ (แก้แล้ว 2026-09-04): ปุ่มแฮมเบอร์เกอร์ผูกกับ
`@onclick="Sidebar.Toggle"` (scoped service `SidebarState`) ซึ่งยิงไม่ออก และต่ำกว่า 900px
sidebar ถูกซ่อนไว้ข้างจอ ปุ่มนั้นคือทางเดียวที่จะเปิดเมนู → **บนมือถือเข้าหน้าอื่นไม่ได้เลย**

**วิธีที่ใช้ตอนนี้:** `wwwroot/js/app.js` (delegated listener บน `document`) จัดการลิ้นชักเมนู
กับการสลับธีมทั้งหมด — ไม่ใช่ C# ข้อดีที่ตามมาคือกดแล้วตอบทันที และยังใช้ได้ตอน circuit กำลัง
reconnect `SidebarState.cs` ถูกลบทิ้งแล้ว **อย่าเอากลับมา**

ถ้าจำเป็นต้องมี component ที่ interactive อยู่ใน layout จริง ๆ ให้ทำเป็น "เกาะ" แบบที่
`<ToastHost @rendermode="InteractiveServer" />` ทำ — มันอยู่ใน circuit เดียวกับ page จึงใช้
`ToastService` (scoped) ตัวเดียวกัน

## 2. หลักการ mobile-first ที่ยึดอยู่

- **ตาราง ↔ การ์ด** — ต่ำกว่า 720px ทุกตารางแสดงเป็นการ์ด (`.card-list.narrow-only`)
  ตั้งแต่ 720px ขึ้นไปกลับไปเป็นตาราง (`.table-scroll.wide-only`)
  ทั้งสองแบบต้องแสดง**ข้อมูลชุดเดียวกัน**เสมอ ห้ามมีฟีเจอร์ที่มีเฉพาะบนจอกว้าง
- **แถบแท็บล่างจอ** (`TabBar.razor`) = การนำทางหลักต่ำกว่า 900px, ไม่เกิน 5 ปุ่ม,
  ปุ่มที่ 5 คือ "เมนู" ที่เปิดลิ้นชักเดิม; ตั้งแต่ 900px ขึ้นไปซ่อน แล้วใช้ sidebar ถาวรแทน
- **touch target** ≥ 44px สำหรับ nav, ≥ 40px สำหรับปุ่มใน toolbar
- **safe area** — ทุกขอบที่ติดจอใช้ `env(safe-area-inset-*)` และ `App.razor` ต้องมี
  `viewport-fit=cover` ไม่งั้น inset จะเป็น 0 เสมอ
- **input บนจอเล็กต้อง 16px** (มี media query `max-width: 480px` ให้แล้ว) ไม่งั้น iOS Safari
  จะซูมหน้าเองตอน focus

## 3. ธีม

สีทุกตัวเป็น token และประกาศครบใน `:root` ก่อนเสมอ แล้วค่อย override ใน
`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` และ `:root[data-theme="dark"]`
(สามสถานะ: สว่าง / มืด / ตามระบบ) — **ห้ามประกาศสีครั้งแรกใน media query** เพราะจะได้จุดที่อ่านไม่ออก
ในโหมดใดโหมดหนึ่งโดยไม่มีใครสังเกต

ค่าที่ผู้ใช้เลือกเก็บใน `localStorage['onion.theme']` (ต่ออุปกรณ์ ไม่ผูกบัญชี) และถูกทาลง `<html>`
ด้วย inline script ใน `<head>` ก่อนวาดจอครั้งแรก เพื่อไม่ให้จอขาววาบ

## 4. PWA

`manifest.webmanifest` + meta ของ Apple ทำให้ติดตั้งลงจอโฮมได้ **จงใจไม่ทำ service worker**:
ทุกอย่างบนหน้านี้คือสถานะแล็บสด การแคชไว้เท่ากับโชว์ของเก่าอย่างมั่นใจ ซึ่งอันตรายกว่าเปิดไม่ติด

## 5. สถานะการทดสอบ

- `dotnet build` ผ่าน 0 error 0 warning
- รันจริงบนพอร์ตแยก (8899, loopback, Development) → `/login`, `/css/theme.css`, `/js/app.js`,
  `/manifest.webmanifest` ตอบ 200 ทั้งหมด
- **ยังไม่ได้ทดสอบด้วยตาบนมือถือจริง** และหน้าที่ต้อง login ยังไม่ได้เห็น เพราะตอนนั้นไม่มี
  OnionProcOparetor.Server รันอยู่บนเครื่อง dev สิ่งที่ต้องลองก่อนเชื่อ: แถบแท็บล่างจอ,

## 6. ทำไม Live View (grid หลายเครื่อง) ถูกถอดออกจากเว็บ — 2026-09-04

**ห้ามใส่กลับโดยไม่แก้ที่ต้นเหตุก่อน**

WPF Console ทำ CCTV grid ได้เพราะเขียน `RfbClient` เองและมี `VncViewMode.Thumbnail` จริง ๆ:
16bpp บน wire (ข้อมูลลดลงครึ่งหนึ่ง) + downscale ตอน decode + throttle การขอ framebuffer ถี่น้อยลงมาก
(ดู `src/OnionProcOparetor.Console/Services/RfbClient.cs`)

ฝั่งเว็บใช้ **noVNC ซึ่งไม่มีโหมดนั้นเลย** — `rfb.scaleViewport = true` ย่อภาพ *หลัง* framebuffer
ความละเอียดเต็มวิ่งข้ามสายมาและถูก decode ใน JS เรียบร้อยแล้ว แปลว่า tile ขนาด 220px ก็ยังรับภาพ
1920×1080 เต็ม ๆ อยู่ดี ของเดิมตั้ง `MaxTiles = 12` → 12 สตรีมความละเอียดเต็ม:

- ทั้ง 12 สายวิ่งผ่าน `VncBridgeEndpoint` ในโปรเซสเดียว แล้วออก uplink เส้นเดียวไปหามือถือ
  ถ้า Tailscale ต่อตรงไม่ได้แล้วตกไปใช้ DERP relay ยิ่งแย่ลงอีก
- มือถือต้อง decode 12 canvas พร้อมกันด้วย JS บน main thread
- ยิง `StartVncSession` พร้อมกัน 12 คำสั่ง → agent 12 เครื่องปลุก winvnc พร้อมกัน แต่ละ tile รอ timeout เอง 20 วิ
- `MaxTiles` เป็นการจำกัดฝั่ง client เท่านั้น — ครู 2 คนเปิดพร้อมกัน = 24 session ไม่มีอะไรกั้น
- `VncBridgeEndpoint` เรียก `GetClientsAsync()` ทุกครั้งที่ต่อ → +12 REST call ต่อการเปิดหนึ่งครั้ง
- และตาม `[[project_vnc_refused_diagnosis]]` ฝั่ง WiFi เป็นคนละ subnet อยู่แล้ว VNC ก็ต่อไม่ติดอยู่ดี

**สิ่งที่ยังอยู่:** Screen View (ทีละเครื่อง, เปิดจากรายการ Clients), `VncBridgeEndpoint`,
`vncInterop.js`, และ Live View ของ WPF Console — ไม่แตะทั้ง Server และ Agent เลย ไม่มี API ตัวไหนถูกลบ

**ที่เพิ่มมาแทน:** ปุ่ม "เครื่องก่อนหน้า / เครื่องถัดไป" ใน Screen View เพื่อไล่ดูทั้งห้องทีละเครื่อง
ซึ่งเป็นงานที่ grid เคยทำ แต่ทำในรูปแบบที่มือถือรับไหว

**บั๊กที่เจอตอนรื้อ:** `VncView.StartAsync()` ถูกเรียกแบบ fire-and-forget (`_ = StartAsync()`)
โดยไม่มี try/catch → exception หายไปเงียบ ๆ และหน้าจอค้างที่ "กำลังขอเปิด session..." ตลอดกาล
ตอนนี้ครอบ try/catch แล้ว ขึ้นข้อความจริงพร้อมปุ่ม "ลองใหม่" — และข้อความนี้เองที่ทำให้เจอบั๊กข้อถัดไป

> ถ้าอยากได้ grid กลับมาจริง ๆ ต้องทำ downscale ฝั่ง server ก่อน (proxy ถอด RFB แล้วย่อภาพส่งต่อ)
> ไม่ใช่แค่เพิ่มหน้า Razor กลับเข้าไป

## 7. noVNC: ต้องใช้ `core/` ไม่ใช่ `lib/` และตอนนี้เก็บไว้ในเครื่องแล้ว — 2026-09-04

อาการที่เจอตอนทดสอบจริง: Screen View ขึ้น
`เปิดหน้าจอไม่สำเร็จ: exports is not defined ... /@novnc/novnc@1.4.0/lib/rfb.js:4:23`

**สาเหตุ:** npm package ของ noVNC มีสองบิลด์
- `core/` = ES module ตัวจริง ← อันที่เบราว์เซอร์ต้องใช้
- `lib/` = CommonJS ที่ทรานส์ไพล์ไว้ให้ Node ← ของเดิม import อันนี้

พอเบราว์เซอร์ `import()` ไฟล์ CommonJS มันไปเจอ `exports.xxx = ...` ซึ่งไม่มี `exports` ใน scope → พังทันที
ไม่เกี่ยวกับเน็ตหรือ CDN เลย (ข้อความ error ที่เดาว่าเป็นเรื่องเน็ตนั้นเดาผิด แต่ทำให้เห็นปัญหาเร็วขึ้น)

**แก้แล้วสองชั้น:**
1. ชี้ไป `core/rfb.js` ที่ถูกต้อง
2. **ย้าย noVNC 1.4.0 มาไว้ที่ `wwwroot/lib/novnc/` เลย** (`core/` + `vendor/pako` + `LICENSE.txt`,
   MPL-2.0, ~50 ไฟล์ 666KB) ไม่พึ่ง CDN อีกต่อไป — แอปนี้เข้าได้แค่ผ่าน tailnet
   ถ้ามือถือใช้ exit node หรือเน็ตโรงเรียนบล็อก CDN จะเปิดคอนโซลได้แต่โหลดตัวถอดรหัสภาพไม่ได้
   ทุกอย่างที่แอปต้องใช้ควรมาจาก origin เดียวกัน

**ตรวจแล้ว:** ไล่ crawl กราฟ import ทั้งหมดผ่าน HTTP จริง — 45 โมดูล ตอบ 200 ครบ,
content-type `text/javascript` ทุกไฟล์, ไม่เหลือ URL ภายนอกแม้แต่ตัวเดียว

**เวลาอัปเกรดเวอร์ชัน:** ดึง tarball จาก npm แล้วคัดมาเฉพาะ `core/` กับ `vendor/` (ห้ามเอา `lib/`)
วางทับที่เดิม แล้ว crawl ซ้ำ

## 8. บั๊ก layout ที่เจอจากภาพหน้าจอจริง — 2026-09-04

`.app-shell` เป็น `display: flex` เฉย ๆ (แถวนอน) ส่วนลูกที่ยังอยู่ใน flow มีแค่ header (sticky) กับ `<main>`
— sidebar/backdrop/tab bar เป็น `position: fixed` หมด ผลคือ**บนมือถือ header ถูกจัดเป็นคอลัมน์แคบ ๆ ทางซ้าย
แล้วเนื้อหาไปอยู่ข้าง ๆ** ไม่ได้เป็นแถบเต็มความกว้างด้านบนอย่างที่ตั้งใจ
เดสก์ท็อปไม่เห็นปัญหาเพราะ header เป็น `display: none`

แก้เป็น `flex-direction: column` — และเป็นเหตุผลว่าทำไมต้องดูของจริงบนมือถือ ไม่ใช่แค่ build ผ่าน

นอกจากนี้ `:focus-visible` เดิมตั้ง `border-radius: 2px` ซึ่งไม่ได้ไปโค้งเส้น outline แต่ไป**เปลี่ยนรูปทรงของ
ปุ่มเอง**ตอนถูก focus (ปุ่มกลม 44px กลายเป็นเหลี่ยมตอนแตะ) เอาออกแล้ว เบราว์เซอร์วาด outline
ตามความโค้งของ element ให้อยู่แล้ว

## 9. ปุ่มสลับธีมบนหัวจอ = 2 สถานะ

ปุ่มบน header สลับสว่าง/มืดตรง ๆ เทียบกับ**ธีมที่เห็นอยู่ตอนนั้น** (`resolved()`)
ไม่ใช่วน 3 สถานะแบบเดิม เพราะปุ่มเดียววน 3 สถานะมีปัญหา: ตอนอยู่ที่ "ตามระบบ" ผู้ใช้ไม่รู้ว่ากดแล้วจะไปทางไหน
และบางจังหวะกดแล้วเหมือนไม่มีอะไรเกิดขึ้น (เพราะ OS ตั้งไว้ตรงกับธีมที่แสดงอยู่พอดี)
ส่วน "ตามระบบ" ยังเลือกได้ในหน้า Settings ซึ่งแสดงครบทั้ง 3 ตัวเลือกให้เห็นพร้อมกัน

## 10. หนึ่งหน้าจอ = หนึ่ง vertical scroll

ห้ามใส่ `max-height` + `overflow-y` ให้ `.table-scroll` อีก (เคยใส่ 74vh เพื่อให้หัวตาราง sticky ทำงาน)
ผลคือมี scrollbar แนวตั้งสองอันบนจอเดียว — ของหน้าเว็บกับของตาราง — นิ้ว/ลูกกลิ้งทำงานคนละอย่าง
ขึ้นกับว่าอยู่ตรงไหน และพอเลื่อนตารางจนสุดก็ต้องเลื่อนอีกชุดเพื่อไปต่อ

`.table-scroll` เหลือแค่ **overflow-x** (ตารางกว้างเกินจอ เลื่อนข้างในกล่องตัวเอง) ส่วนแนวตั้งเป็นของหน้าเว็บอย่างเดียว

และ **หัวตาราง sticky ถูกถอดออกไปด้วย ไม่ได้ทิ้งไว้เป็น CSS ตาย** เพราะมันทำงานไม่ได้อยู่แล้ว:
กล่องที่มี `overflow-x: auto` จะเป็น scroll container ทั้งสองแกนตามสเปก (ค่า `visible` ของอีกแกนจะกลายเป็น `auto`)
`<th>` ที่ sticky ข้างในจึงยึดกับ scrollport ของกล่องนั้น ไม่ใช่ของหน้าเว็บ พอกล่องไม่เลื่อนแนวตั้งก็ไม่มีอะไรให้ยึด
ถ้าอยากได้จริง ๆ ต้องเปลี่ยนทั้งแอปเป็น app-shell (หน้าเว็บไม่เลื่อน ให้พื้นที่เนื้อหาเป็น scroller อันเดียว)
ซึ่งใหญ่เกินกว่าที่หัวตารางติดขอบจะคุ้ม

ตัวที่ยังเลื่อนแนวตั้งได้และถูกต้องมีแค่ 2 จุด: `.sidebar-nav` (ลิ้นชักเมนู) กับ `.modal` (ตัว sheet เอง)

## 11. ทำไมรู้สึกช้า/แข็ง และแก้อะไรไปบ้าง — 2026-09-04

ต้นเหตุคือสถาปัตยกรรมของ Blazor Server เอง: **ทุกการกดหนึ่งครั้ง = ไป-กลับผ่าน SignalR หนึ่งรอบ**
เซิร์ฟเวอร์ re-render แล้วส่ง DOM diff กลับมา บนมือถือผ่าน Tailscale นั่นคือความเงียบหนึ่งจังหวะทุกครั้งที่แตะ

แก้ 4 จุดที่รู้สึกได้ที่สุด (ไม่ได้แก้ตัวสถาปัตยกรรม):

1. **`SearchBox.razor` (ใหม่) — debounce 300ms + ไม่ two-way bind**
   ของเดิมใช้ `@bind:event="oninput"` = ยิงไปเซิร์ฟเวอร์ทุกตัวอักษร แล้ว re-render ทั้งตารางและการ์ด
   ที่สำคัญกว่า debounce คือ**เลิก bind ค่ากลับ**: เมื่อเซิร์ฟเวอร์ echo ค่ากลับมาเขียนทับ input
   ตัวอักษรจะสลับ/หายกลางคำได้บนเน็ตช้า พอปล่อยให้ browser คุม input เอง การพิมพ์เร็วเสมอไม่ว่า latency เท่าไร
2. **Optimistic update** ที่ Rules (เปิด/ปิดกฎ) และ Program Review (อนุญาต/บล็อก)
   ของเดิม: เรียก API → reload ทั้งชุด → ค่อยเปลี่ยนภาพ = รอ 2 รอบเน็ตต่อการกดหนึ่งครั้ง
   ซึ่งอ่านเหมือน "กดไม่ติด" แล้วคนก็กดซ้ำ (ซึ่งของ Rules คือสลับกลับทันที — อันตราย)
   ตอนนี้เปลี่ยนภาพทันที แล้วย้อนกลับ + toast ถ้าเซิร์ฟเวอร์ปฏิเสธ
   **ใช้ได้เฉพาะงานที่ย้อนกลับได้และเห็นผลชัด** ห้ามใช้กับงานที่ย้อนไม่ได้
3. **ไฮไลต์เมนูทันที + progress bar** (`app.js`) — ย้าย `.active` ให้เลยตอนแตะ ไม่รอ re-render
   และขึ้นแถบบางด้านบนจนกว่า enhanced navigation จะจบ (มี timeout 8 วิกันค้าง)
4. **transition ที่ badge/การ์ด** — สถานะเปลี่ยนแบบค่อย ๆ แทนกระตุก ซึ่งเป็นที่มาของความรู้สึก "แข็ง"

**ยังเหลือ (ทำต่อได้ถ้ายังรู้สึกช้า):** ตอนนี้ทุกหน้า render **ทั้งตารางและการ์ดพร้อมกัน** แล้วซ่อนอันหนึ่งด้วย CSS
แปลว่า DOM และงาน diff เป็นสองเท่า วิธีแก้คือให้ JS รายงานความกว้างจอเข้ามาแล้ว render แค่แบบเดียว
(ยังไม่ทำเพราะกระทบ 6 หน้าและเสี่ยง regression มากกว่าที่ได้)

## 12. เรื่อง library — ที่รับมาและที่ปฏิเสธ

**รับมา (ไม่ใช่ dependency ใหม่สักตัว):**
- `qualityLevel` / `compressionLevel` ของ noVNC เอง (ตั้ง 5 / 6) — ลด bandwidth VNC โดยตรง ของมีอยู่แล้วในตัว
- Fullscreen API + Screen Orientation API ของเบราว์เซอร์ — ไม่ต้องใช้ `screenfull.js` เพราะเขียนเองแค่ ~20 บรรทัด
- จุด extension ของ Blazor เองสำหรับ reconnect modal (`id="components-reconnect-modal"`)

**ปฏิเสธ พร้อมเหตุผล:**
- **MudBlazor / Radzen / Blazorise** — *ไม่ได้แก้ปัญหาที่เป็นอยู่* ความช้ามาจาก round-trip ของ Blazor Server
  ไม่ใช่จากคุณภาพ component และ library พวกนี้ก็รันบน circuit เดียวกัน แลกมาด้วยการเขียนใหม่ ~20 component,
  CSS/JS เพิ่มหลายร้อย KB, ระบบ theme ของเขาชนกับ token ที่ทำให้ตรงกับ WPF Console
  และ DataGrid ของเขาบนจอ 360px ก็คือตารางเลื่อนข้าง — สิ่งที่เพิ่งเปลี่ยนเป็นการ์ดไป
- **Blazor WebAssembly** — แก้ latency ได้จริงเพราะ interaction ไม่ต้องวิ่งไปเซิร์ฟเวอร์
  แต่ต้องรื้อ auth (token ตอนนี้ไม่เคยออกจากเซิร์ฟเวอร์เลย) + โหลด runtime หลาย MB ครั้งแรกผ่าน Tailscale
  เป็นโปรเจกต์ ไม่ใช่การปรับ
- **Alpine.js / htmx** — ชนกับ Blazor โดยตรง เพราะ Blazor เป็นเจ้าของ DOM และ diff ทับสิ่งที่ library อื่นแก้
- **NProgress.js** — 5KB + CSS สำหรับสิ่งที่เขียนเองแล้ว 25 บรรทัด และต้องกลับไปพึ่ง CDN อีก
- **ชุดไอคอน (Lucide/Feather)** — ตอนนี้ inline ~30 ไอคอนที่ใช้จริง ถ้าใช้ package ต้องเลือกระหว่าง CDN
  (เพิ่งเอาออก) หรือ vendor ไอคอนพันกว่าตัวที่ไม่ได้ใช้
- **QuickGrid / `<Virtualize>`** (ของ Microsoft เอง ไม่ใช่ของนอก) — มีประโยชน์จริงถ้ารายการโตเกิน ~500 แถว
  ตอนนี้ 40 เครื่อง / 100 log ยังไม่คุ้มกับการรื้อ dual rendering ที่ทำไว้ **เก็บไว้เป็นทางเลือกถัดไป**

## 13. บั๊กที่เจอจากการรีวิวด้วย mock server — 2026-09-04

รีวิวโดยรัน OnlineConsole บนพอร์ตแยก (8899, loopback) ชี้ไป **mock server** ที่เขียนขึ้นเอง
(`Server__BaseUrl=http://127.0.0.1:8901`) แล้ว login ผ่าน curl เพื่อดึง HTML ของทุกหน้าออกมาอ่านจริง
วิธีนี้ไม่แตะ Server จริง ไม่แตะฐานข้อมูลจริง และไม่รบกวนคนที่กำลังใช้อยู่

**บั๊ก 1 — `value="_search"` โผล่ในช่องค้นหา (ผู้ใช้เจอเอง)**
```razor
<SearchBox Value="_search" ... />   <!-- ผิด: ได้ข้อความ "_search" -->
<SearchBox Value="@_search" ... />  <!-- ถูก -->
```
Razor ปฏิบัติกับ parameter **ชนิด string** ที่ไม่มี `@` เป็น *literal* ต่างจาก parameter ชนิดอื่น
(`int`, `bool`, `DateTime`, object) ที่ Razor ตีความเป็นนิพจน์ให้เอง — จึงไม่มี error ตอน build
ไม่ใช่แค่เรื่องหน้าตา: ผู้ใช้พิมพ์ต่อท้ายกลายเป็น `_searchCOM-2` แล้วกรองไม่เจอสักรายการ
โดนทั้ง Home, Logs, AuditLog, RunningProcessesModal — แก้ครบแล้ว
**เวลาเขียน component ใหม่ที่มี parameter เป็น string ให้เช็คทุกครั้งว่ามี `@` หรือยัง**

**บั๊ก 2 — กล่อง reconnect หายไปใน 2 สถานะ**
อ่าน state machine จริงใน `blazor.web.js` (.NET 10, class `Go`) แล้วพบว่า:
- `pause()` **ถอด** `-show` และ `-retrying` ออก แล้วใส่ `-paused`
- `failed()` ใส่ `-resume-failed` แทน `-failed` ถ้าเป็นการ resume ไม่ใช่ reconnect

ของเดิมรองรับแค่ show/failed/rejected → สองสถานะนั้นจะทำให้ overlay **หายไปทั้งกล่อง**
เหลือหน้าค้างเฉย ๆ ไม่มีอะไรอธิบาย ตอนนี้รองรับครบ 6 สถานะ + ช่องนับถอยหลัง
(`#components-seconds-to-next-attempt`) และ maxRetries จริงคือ 30 ไม่ใช่ 8

**เครื่องมือที่ใช้ตรวจ (เก็บไว้ใช้ซ้ำได้):**
- `node --check` กับ `app.js` / `vncInterop.js` — จับ syntax error ที่จะทำให้ทั้งไฟล์ตายเงียบ ๆ
- DOM stub ใน node รัน `app.js` จริงแล้วยิง event ทดสอบ 20 เคส (ธีมสลับ 2 สถานะ, ลิ้นชัก,
  ไฮไลต์แท็บ, progress bar, fullscreen ตอน orientation lock ถูกปฏิเสธแบบ iOS)
- ไล่ crawl asset ทุกตัวที่หน้าอ้างถึง → 200 ครบ, ไม่มี id ซ้ำ, CSS วงเล็บปีกกาสมดุล

## 14. ข้อควรระวังตอนแก้ไฟล์ระหว่างที่ระบบ live อยู่

ยืนยันด้วยการทดสอบแล้ว: instance ที่รันด้วย `dotnet run` **เสิร์ฟ `wwwroot/` ตรงจากโฟลเดอร์ source**
(ผ่าน static web assets manifest) แปลว่า

- แก้ `theme.css` / `app.js` / ไฟล์ใน `wwwroot` = **มีผลกับคนที่ใช้อยู่ทันที** ไม่ต้อง restart
- แก้ `.razor` / `.cs` = **ไม่มีผลจนกว่าจะ restart**

เวลามีคนใช้งานอยู่ ต้องรู้ว่ากำลังแก้ฝั่งไหน และอย่า build ทับ `bin/` ของ instance ที่รันอยู่
(ใช้ `dotnet build -o <โฟลเดอร์อื่น>` แทน)
